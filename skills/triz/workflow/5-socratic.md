# Stage 5: Validate with Socratic questions

**Goal:** test the top options with the user before committing to one, so the
plan survives contact with the real situation.

## Steps

1. Present the top 2-3 options from stage 4 in a few lines each.
2. Ask **one question at a time** from the bank below. Wait for the answer.
3. After each answer, decide: keep going, change the option, loop back, or stop.
4. Record each question, answer and change for the validation log.

### Which questions to ask

- Ask at least **3 questions of different types**.
- Start with the type most likely to break the leading option. Usually that is
  **Consequences** or **Viewpoints**.
- Use **Clarification** when an answer is vague, not as an opener.
- Use **The question itself** when answers keep drifting away from the
  contradiction.
- Fill the `<...>` with specifics. A question about "the macros" beats a
  question about "the solution".

## Question bank

### Clarification

1. When you say <word>, what exactly do you mean?
2. Can you give an example of <claim> from the last month?
3. What would <option> look like on its first day?
4. Who exactly would do <step>?
5. How would you tell that <option> is working?

### Assumptions

1. What are we assuming must stay the same here?
2. Why do you think <constraint> can't change?
3. What would have to be true for <option> to fail?
4. Are we assuming <resource> will be available when needed?
5. Is <belief> something you know, or something the team takes for granted?

### Evidence

1. What tells you <option> would work here?
2. Have you seen something like <option> work elsewhere? What was different?
3. What data do you already have that supports or contradicts this?
4. How could we test <option> cheaply before committing?
5. What result in the first two weeks would make you drop it?

### Viewpoints

1. Who would object to <option>, and why?
2. How would <stakeholder> describe this problem?
3. What would a customer, user or outsider notice first?
4. Who loses something if <option> happens?
5. If a competitor or a peer solved this, how would they do it?

### Consequences

1. What new problem does <option> create?
2. What happens in six months if <option> works exactly as planned?
3. What happens if it only half works?
4. What does <option> make harder to do later?
5. If <option> goes wrong, how bad is it and how easy to undo?

### The question itself

1. Is this still the problem you want solved?
2. If <option> worked, would the original symptom go away?
3. Is <B> really what gets worse, or is something else the limit?
4. Would you still want this if <constraint> disappeared tomorrow?
5. Is there a bigger problem that this one is part of?

## Stop rules

Stop and move to stage 6 when one of these happens:

- The user approves an option ("let's do that", "yes, go with 1").
- About 7 questions have been asked and the leading option still stands; ask
  for approval directly.
- The user asks to stop. Note "partly validated" in the plan.

## Loop-back rules

- An answer reveals a **new contradiction** (improving the option worsens
  something important): go back to stage 2 with it. Show the state block so
  the user sees what is kept.
- An answer reveals a **missing constraint or resource**: go back to stage 4,
  re-filter and re-rank.
- An answer shows the **problem was misunderstood**: go back to stage 1.

Each loop-back is listed in the validation log. After two loop-backs, ask the
user whether to continue or settle on the best option so far.

## Fast mode

Ask only 2-3 questions, from Consequences and Viewpoints. Offer to skip:
"I have two quick risk questions, or I can go straight to the plan." If the
user skips, mark the plan "Validated: skipped (fast mode)".

## Output

The approved option, the questions asked with answers, and what changed.

## Gate

Explicit user approval of one option before stage 6.
